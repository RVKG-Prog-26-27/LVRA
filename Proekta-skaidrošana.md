# Latviešu rokrakstu atpazīšana — подробное объяснение проекта

Этот файл объясняет, как устроен весь проект, и особенно подробно —
как устроен и почему именно так спроектирован блок "AI" (модель).
Структура объяснения повторяет структуру блок-схемы: от входа (INPUT)
через AI до выхода (OUTPUT).

---

## 1. Общая картина: зачем нужен весь этот пайплайн

Задача — по изображению рукописной строки текста получить строку символов
(текст). Проблема в том, что:

- на изображении текст занимает **разное количество пикселей** для разных
  букв и слов (широкая "Ш" ≠ узкая "i"),
- мы **не знаем заранее**, где на изображении начинается и кончается
  каждая буква (это и есть неотвеченный вопрос "Teksta zonas
  atpazīšana????" на вашей схеме — вручную это делать не нужно),
- нейросеть при этом устроена так, что легче всего заставить её выдавать
  **фиксированное** количество предсказаний за один проход (по одному на
  каждый "срез" изображения по ширине).

Отсюда возникает несоответствие: сеть выдаёт, скажем, 40 предсказаний
подряд, а в слове на картинке — 8 букв. Как из 40 "сырых" предсказаний
получить 8 букв? Именно для этого в пайплайн добавлен **CTC** (об этом —
в разделе 5). Это тот элемент, которого на исходной блок-схеме не было
вообще, и без которого AI-блок в том виде, в каком он был нарисован
(CNN и BiLSTM как два отдельных, не связанных друг с другом блока),
попросту не может работать.

Полный путь данных:

```
изображение строки (произвольной ширины, высота приведена к 32 px)
        │
        ▼
   ┌─────────┐
   │   CNN   │   вытягивает визуальные признаки, сжимает высоту до 1
   └─────────┘   (это "Līnijas atpazīšana" + "Pareiza novietošana" со схемы)
        │
        ▼   картинка height×width  →  последовательность из T "срезов"
   ┌─────────┐
   │ BiLSTM  │   смотрит на всю последовательность признаков и учитывает
   │  (x2)   │   контекст слева и справа от каждой позиции
   └─────────┘   (это "Vārdu atpazīšana" + "Pieturzīmes" + "Cipari" со схемы)
        │
        ▼   на каждом из T шагов — вектор вероятностей по всем символам
   ┌─────────┐
   │ Linear  │   переводит вектор признаков BiLSTM в "оценки" по каждому
   └─────────┘   символу алфавита (включая blank)
        │
        ▼
   ┌─────────┐
   │   CTC   │   выравнивает T предсказаний в итоговый текст произвольной
   └─────────┘   длины (на схеме отсутствовал)
        │
        ▼
     ТЕКСТ  ("Teksts digitālajā veidā" → "Teksta rakstīšana" на схеме)
```

## 2. Алфавит и кодирование (`alphabet.py`)

Сеть работает с числами, а не с буквами, поэтому нужен словарь
"символ → число" и обратно. Это уже подробно разобрано в отдельном
объяснении (см. предыдущий ответ в чате), кратко:

- `ALPHABET` — список всех допустимых символов, индекс 0 зарезервирован
  под специальный символ **blank** (о нём — в разделе 5).
- `encode(text)` — строка → список чисел (без blank).
- `decode_greedy(indices)` — список чисел (с blank и повторами) → строка.
- `NUM_CLASSES = len(ALPHABET)` — это число одновременно является
  размером **последнего слоя сети** (сколько классов она должна уметь
  различать на каждом шаге).

Этот файл — фундамент, от него напрямую зависит архитектура модели:
выходной слой `Linear` в `model.py` обязан иметь ровно `NUM_CLASSES`
выходов, иначе CTC не сможет сопоставить предсказания с текстом.

## 3. Данные: откуда берутся примеры для обучения (`synthetic_data.py`, `dataset.py`)

Прежде чем создавать AI, нужно то, на чём его учить. На схеме это ветка
"Informācija/Datu sakopšana" → "Rokrakstu bāzes sagatavošana" →
"Reāli dati" / "Sintētiskie dati".

### 3.1 Синтетические данные (`synthetic_data.py`)

Поскольку реальных сканов рукописного текста пока нет, используется
**генератор**: берётся случайная латышская фраза из встроенного списка
(`_default_corpus()`, или `data/corpus.txt`, если вы его создадите),
рисуется шрифтом (`ImageFont.truetype`) на белом фоне, и затем
**искажается**, чтобы хоть немного имитировать вариативность рукописного
письма:

- `rotate(angle)` — случайный поворот на ±3°,
- `transform(..., AFFINE, ...)` — сдвиг (shear), имитирующий наклон
  почерка,
- `GaussianBlur` — лёгкое размытие,
- добавление гауссовского шума на пиксели.

Это **временная заглушка**, а не полноценная замена реальных данных —
честно об этом сказано и в коде, и в README. Модель, обученная только
на таких данных, выучит распознавать *печатный, слегка деформированный*
текст, а не настоящий почерк. Как только появятся реальные сканы —
нужно либо полностью переключиться на них (`RealHTRDataset`), либо
смешивать (это уже поддержано в `train.py` через `--real-data`).

### 3.2 Реальные данные (`dataset.py`, класс `RealHTRDataset`)

Ожидает папку с изображениями и файл `labels.csv` (`filename,text`).
Это ровно тот самый шаг "Rokrakstu bāzes sagatavošana" со схемы —
подготовка размеченной базы: кто-то (человек) сопоставляет каждому
отсканированному изображению строки её текстовую расшифровку.

### 3.3 Приведение изображений к общему виду

И синтетические, и реальные изображения перед подачей в сеть проходят
через одинаковую подготовку:

```python
def image_to_tensor(img: Image.Image) -> torch.Tensor:
    arr = np.array(img.convert("L"), dtype=np.float32) / 255.0
    arr = 1.0 - arr  # инвертируем: фон = 0, чернила ≈ 1
    return torch.from_numpy(arr).unsqueeze(0)  # [1, H, W]
```

Два важных момента:
- **Высота всегда фиксирована** (`TARGET_HEIGHT = 32`), ширина —
  произвольная (пропорционально масштабируется). Это принципиально: CNN
  ниже спроектирована так, чтобы сжимать именно высоту до 1, а ширину
  превращать в "временную" ось последовательности.
- **Инверсия цвета** (фон 0, чернила ~1) — так сети проще: интересующая
  нас информация (штрихи) представлена ненулевыми значениями, а не
  нулевыми, как было бы с обычным чёрным-на-белом.

### 3.4 Батчи переменной ширины (`collate_batch`)

Так как строки разной длины дают изображения разной ширины, а тензор в
батче должен быть прямоугольным, все изображения в батче **дополняются
белым (нулями) до ширины самого широкого** изображения в этом батче.
Реальная ширина каждого изображения дополнительно сохраняется в
`widths` — на случай, если понадобится не учитывать "поддельные" пиксели
при более аккуратной реализации (в текущей базовой версии `train.py`
для простоты этого не делает и считает длину выходной
последовательности одинаковой для всего батча — см. раздел 6.2, это
одно из мест для будущего улучшения).

## 4. Модель (`model.py`) — главная часть: как устроен AI

Это исправленная версия блока "AI" со схемы. Разберём по слоям.

### 4.1 Почему CNN и BiLSTM — не параллельные ветки, а последовательные этапы

На исходной схеме от "AI" отходят две **независимые** стрелки: одна к
CNN, другая к BiLSTM. Если бы это было реализовано буквально, получилось
бы два отдельных предсказания текста — одно от CNN, другое от BiLSTM —
и было бы неясно, что с ними делать (усреднять? выбирать одно?). На
практике для распознавания текста используется связка, где **выход
CNN — это вход BiLSTM**:

```
изображение → CNN → последовательность признаков → BiLSTM → символы
```

CNN хорошо справляется с локальными визуальными паттернами (форма
штриха, контур буквы) — это то, что на схеме названо "Līnijas atpazīšana"
(распознавание линий/штрихов) и "Pareiza novietošana" (корректное
пространственное расположение — CNN за счёт свёрток и пулинга сохраняет
информацию о том, *где по горизонтали* какой признак находится).

Но CNN сама по себе "смотрит" только на небольшой локальный кусок
изображения (её рецептивное поле ограничено) и ничего не знает о
контексте — например, что за этой буквой шла другая, и вместе они,
возможно, образуют определённое сочетание. А для различения похожих по
форме букв, для учёта контекста (это буква в начале слова или в
середине, после какого знака препинания) нужна последовательная модель
с памятью — это BiLSTM, которая на схеме отвечает как раз за
"Vārdu atpazīšana" (распознавание слов — то есть учёт контекста всей
последовательности символов), "Pieturzīmes" (знаки препинания) и "Cipari"
(цифры) — все эти категории символов сеть учится различать не по
отдельным "веткам", а благодаря тому, что BiLSTM видит всю строку целиком
и её направление чтения слева направо и справа налево одновременно
(отсюда "Bi" — bidirectional, двунаправленная).

### 4.2 `CNNBackbone` — извлечение признаков

```python
class CNNBackbone(nn.Module):
    def __init__(self):
        super().__init__()
        self.net = nn.Sequential(
            nn.Conv2d(1, 64, 3, 1, 1), nn.ReLU(inplace=True), nn.MaxPool2d(2, 2),      # 32 → 16, W → W/2
            nn.Conv2d(64, 128, 3, 1, 1), nn.ReLU(inplace=True), nn.MaxPool2d(2, 2),    # 16 → 8,  W/2 → W/4
            nn.Conv2d(128, 256, 3, 1, 1), nn.ReLU(inplace=True),
            nn.Conv2d(256, 256, 3, 1, 1), nn.ReLU(inplace=True), nn.MaxPool2d((2, 1), (2, 1)),  # 8 → 4, ширина не трогаем
            nn.Conv2d(256, 512, 3, 1, 1), nn.BatchNorm2d(512), nn.ReLU(inplace=True),
            nn.Conv2d(512, 512, 3, 1, 1), nn.BatchNorm2d(512), nn.ReLU(inplace=True), nn.MaxPool2d((2, 1), (2, 1)),  # 4 → 2
            nn.Conv2d(512, 512, 2, 1, 0), nn.ReLU(inplace=True),  # 2 → 1
        )
```

Что здесь происходит по шагам, если на входе изображение `[1, 32, W]`
(1 канал — градации серого, высота 32, ширина W):

| Слой | Что делает | Высота после | Ширина после |
|---|---|---|---|
| Conv(1→64) + Pool(2,2) | ищет простые признаки (края, штрихи), уменьшает и высоту, и ширину вдвое | 16 | W/2 |
| Conv(64→128) + Pool(2,2) | признаки посложнее (сочетания штрихов) | 8 | W/4 |
| Conv(128→256) ×2 + Pool(**2,1**) | признаки уровня частей букв; пулинг `(2,1)` уменьшает **только высоту**, ширину не трогает — это важно! | 4 | W/4 |
| Conv(256→512) ×2 + BatchNorm + Pool(**2,1**) | признаки уровня целых букв/сочетаний | 2 | W/4 |
| Conv(512→512, kernel=2, pad=0) | последний штрих: сжимает оставшуюся высоту 2 → 1 | **1** | W/4 − 1 |

**Почему пулинг `(2,1)`, а не `(2,2)`, в последних слоях?** Потому что нам
критично важно **не терять разрешение по ширине** — ведь ширина после
всех преобразований станет "временной осью" для BiLSTM: каждый шаг по
ширине должен соответствовать примерно одной позиции в тексте. Если бы
мы продолжали сжимать ширину так же агрессивно, как высоту, у нас
получилось бы слишком мало "тайм-степов" — меньше, чем букв в длинной
строке, и CTC физически не смог бы восстановить текст (T должно быть
**не меньше** длины текста, а с учётом повторов и blank — с запасом
больше).

**Зачем высоту сжимать именно до 1, а не оставлять больше?** Потому что
после этого весь "столбец" признаков по высоте в каждой позиции ширины
превращается в один вектор — то есть изображение размером `[512, 1, W']`
естественно превращается в последовательность из `W'` векторов размерности
512 (после `squeeze(2)` и `permute` в `CRNN.forward`, см. ниже). Если бы
высота была больше 1, пришлось бы придумывать, как схлопывать несколько
"строк" признаков в одну последовательность — это только усложнило бы
архитектуру без реальной пользы (в рукописной строке нет отдельных
"визуальных полос", которые имело бы смысл рассматривать по отдельности
на этом уровне).

**Зачем `BatchNorm2d`?** Стабилизирует обучение на более глубоких слоях
(нормализует активации), в оригинальной статье про CRNN (2015,
"An End-to-End Trainable Neural Network for Image-based Sequence
Recognition") это тоже присутствует и на практике заметно ускоряет и
стабилизирует сходимость по сравнению с сетью без BatchNorm.

### 4.3 Переход от "картинки" к "последовательности" (`CRNN.forward`)

```python
def forward(self, images):
    feats = self.cnn(images)          # [B, 512, 1, W']
    feats = feats.squeeze(2)          # [B, 512, W']       — убрали высоту (она уже 1)
    feats = feats.permute(2, 0, 1)    # [W'(=T), B, 512]    — переставили оси
    logits = self.rnn(feats)          # [T, B, num_classes]
    return logits.log_softmax(dim=2)
```

Это самый концептуально важный момент всего пайплайна: **ширина
изображения после CNN становится осью времени T для рекуррентной сети**.
Иными словами, мы буквально "читаем" изображение слева направо, и на
каждом шаге BiLSTM получает вектор из 512 чисел, описывающий, что за
визуальные признаки находятся в этом узком вертикальном "срезе"
изображения.

`permute(2, 0, 1)` меняет порядок осей на `[T, B, C]`, потому что
`nn.LSTM` в PyTorch по умолчанию (`batch_first=False`) ожидает именно
такой порядок: сначала время, потом батч, потом признаки.

### 4.4 `BiLSTMHead` — учёт контекста

```python
class BiLSTMHead(nn.Module):
    def __init__(self, in_dim, hidden, num_classes, num_layers=2):
        super().__init__()
        self.lstm = nn.LSTM(in_dim, hidden, num_layers=num_layers,
                             bidirectional=True, batch_first=False)
        self.fc = nn.Linear(hidden * 2, num_classes)

    def forward(self, x):
        out, _ = self.lstm(x)   # [T, B, hidden*2]
        return self.fc(out)     # [T, B, num_classes]
```

- **LSTM** (Long Short-Term Memory) — рекуррентная сеть с "памятью",
  умеющая учитывать предыдущие шаги последовательности при обработке
  текущего. Здесь `num_layers=2` — два слоя LSTM друг над другом (второй
  слой обрабатывает выход первого), это даёт более сложные, абстрактные
  зависимости, чем один слой.
- **Bidirectional** — на самом деле внутри работают **две** LSTM: одна
  читает последовательность слева направо, другая — справа налево, а их
  выходы на каждом шаге склеиваются (`hidden * 2` — отсюда и умножение
  на 2 в `Linear`). Это важно для текста: чтобы правильно распознать
  символ, часто полезно знать не только то, что было *до* него, но и
  то, что будет *после* (например, отличить строчную "b" от похожей на
  неё формы, если контекст справа подсказывает, что это конец слова).
- **`Linear(hidden*2, num_classes)`** — финальный классификатор: для
  каждого из T шагов превращает вектор признаков BiLSTM в набор "очков"
  (logits) по каждому символу алфавита, включая blank.
- **`log_softmax(dim=2)`** — превращает эти очки в логарифмы вероятностей
  (в сумме по классам на каждом шаге дают 1 после `exp`). Логарифм, а не
  просто вероятности, используется потому, что `nn.CTCLoss` в PyTorch
  **ожидает на входе именно log-вероятности** — так численно стабильнее
  считать очень маленькие произведения вероятностей по длинной
  последовательности (иначе числа стали бы слишком малы и "обнулялись"
  бы при обычной точности вычислений).

## 5. CTC — то, чего не было на схеме, но без чего AI не работает

CTC (Connectionist Temporal Classification) — это не отдельный "слой" с
обучаемыми весами, а способ **посчитать функцию потерь** и способ
**раскодировать** предсказания, специально созданный для задач, где:

- длина входа (T шагов от CNN) не совпадает с длиной выхода (число
  символов в тексте),
- заранее неизвестно выравнивание — какой шаг T соответствует какой
  букве.

### 5.1 Что такое blank

Отдельно подробно разобрано в `alphabet.py` (см. предыдущее объяснение в
чате). Коротко: blank (индекс 0) — служебный символ, который сеть может
предсказывать между одинаковыми соседними буквами, чтобы при
декодировании (`decode_greedy`: схлопнуть повторы → убрать blank) они не
слиплись в одну, и в местах, где сеть "ещё не решила" или где визуально
нет нового символа.

### 5.2 Обучение: `nn.CTCLoss`

```python
ctc_loss = torch.nn.CTCLoss(blank=0, zero_infinity=True)
...
loss = ctc_loss(log_probs, targets, input_lengths, target_lengths)
```

Что тут происходит математически (без формул, на пальцах): CTCLoss
перебирает **все возможные способы** расставить T предсказаний так,
чтобы после схлопывания повторов и удаления blank получился именно
правильный текст, и считает функцию потерь так, чтобы сеть постепенно
увеличивала суммарную вероятность *всех* таких правильных вариантов
выравнивания. Модели не нужно заранее знать "точное" выравнивание —
CTCLoss сама во время обучения учитывает все возможные варианты и
подсказывает сети, в какую сторону двигать веса.

Аргументы:
- `log_probs` — выход модели, `[T, B, num_classes]`.
- `targets` — правильный текст в виде чисел, **без** blank, все тексты
  батча склеены в один плоский список (`targets.extend(enc)` в
  `train.py`).
- `input_lengths` — сколько шагов T реально "валидны" для каждого
  примера в батче (в текущей простой реализации у всех элементов батча
  одинаковое T, так как задаётся длиной после padding — см. раздел 6.2,
  это упрощение).
- `target_lengths` — длина текста (в символах) для каждого примера
  батча.
- `zero_infinity=True` — защита от редкого случая, когда T оказывается
  меньше длины текста (тогда выровнять физически невозможно, и без
  этого флага loss стал бы `inf` и сломал обучение); такие случаи
  просто обнуляются, а не роняют тренировку.

### 5.3 Инференс: greedy decoding

В `infer.py`:

```python
log_probs = model(image_tensor)                 # [T, 1, C]
pred_indices = log_probs.argmax(dim=2)...        # на каждом шаге — самый вероятный класс
return decode_greedy(pred_indices)               # схлопнуть + убрать blank
```

На инференсе (в отличие от обучения) не нужно перебирать все варианты
выравнивания — достаточно на каждом шаге взять класс с максимальной
вероятностью (`argmax`) и применить то же самое правило декодирования
"схлопнуть повторы → убрать blank". Это самый простой и быстрый способ
(**greedy**, "жадный"), но не самый точный: более продвинутый вариант —
**beam search** (перебор нескольких лучших гипотез параллельно,
возможно, с языковой моделью, которая штрафует маловероятные
последовательности букв) — в этой базовой версии не реализован, это
один из очевидных путей для дальнейшего улучшения точности.

## 6. Обучение (`train.py`)

### 6.1 Общий цикл

1. Взять батч изображений + текстов (`DataLoader` + `collate_batch`).
2. Прогнать изображения через модель → `log_probs [T, B, C]`.
3. Закодировать тексты в числа, посчитать `CTCLoss`.
4. `loss.backward()` — посчитать градиенты.
5. `clip_grad_norm_(..., 5.0)` — обрезать слишком большие градиенты
   (частая практика для RNN/LSTM, которые склонны к "взрывающимся"
   градиентам на длинных последовательностях; без этого обучение может
   стать нестабильным, loss будет "скакать" или уходить в NaN).
6. `optimizer.step()` — обновить веса (используется Adam — адаптивный
   метод оптимизации, хорошо работает "из коробки" почти для любых
   архитектур, отсюда выбор по умолчанию для базовой версии).
7. Периодически сохранять чекпоинт (`torch.save(model.state_dict(), ...)`).

### 6.2 Известное упрощение: одинаковое T для всего батча

```python
T = log_probs.size(0)
input_lengths = torch.full((images.size(0),), T, dtype=torch.long)
```

Так как изображения в батче дополнены (padded) до одинаковой ширины
(раздел 3.4), после CNN у них у всех получается одинаковое T — и код
просто говорит "для всех примеров в батче валидны все T шагов". Это
работает, но не совсем точно: у более коротких (до паддинга) изображений
часть "хвоста" T на самом деле — это признаки из пустого белого
паддинга, а не из реального текста. Для базовой версии это допустимо
(сеть достаточно быстро учится игнорировать пустые области), но более
аккуратная реализация должна была бы вычислять `input_lengths`
индивидуально для каждого примера, опираясь на сохранённые `widths` из
`collate_batch`, через ту же формулу, что в `model.output_length()`.

## 7. Как менялась блок-схема — итог

| На схеме | Проблема | Как исправлено в коде |
|---|---|---|
| CNN и BiLSTM — параллельные независимые ветки от "AI" | Неясно, как совместить два независимых предсказания текста | CNN → BiLSTM последовательно, выход одного — вход другого |
| Нет блока после BiLSTM, кроме голого списка задач ("Vārdu atpazīšana" и т.д.) | Непонятно, как из признаков получить конкретные символы | Добавлен `Linear` классификатор + `log_softmax` |
| Нет ничего похожего на выравнивание переменной длины | Число "шагов" сети (T) не совпадает с числом букв в тексте | Добавлен CTC (loss при обучении + greedy decode при инференсе), плюс специальный символ **blank** |
| "Teksta zonas atpazīšana????" — с явными знаками вопроса на схеме, то есть неясный шаг | Нужно ли сегментировать текст на отдельные буквы перед распознаванием? | Не нужно — благодаря CTC модель принимает изображение целой строки и сама выравнивает выход с текстом |

## 8. Что можно улучшить дальше (в порядке приоритета)

1. **Реальные данные.** Синтетика — это верхняя граница простоты задачи;
   модель, обученная только на ней, скорее всего плохо перенесётся на
   настоящий почерк. Первый и самый важный шаг — собрать хотя бы
   несколько сотен реальных размеченных строк (`RealHTRDataset`).
2. **Индивидуальные `input_lengths`** вместо одинакового T для батча
   (раздел 6.2).
3. **Beam search decoding** вместо greedy — обычно даёт заметный прирост
   точности почти бесплатно (без переобучения модели).
4. **Аугментации, приближенные к реальности**: текстура бумаги, разная
   толщина/цвет чернил, лёгкие искривления строки — как только появятся
   реальные сканы, можно подобрать шум, который их реалистично
   характеризует.
5. **Метрики качества**: сейчас в проекте нет подсчёта CER/WER (Character
   Error Rate / Word Error Rate) на отложенной выборке — без них сложно
   объективно понять, насколько хорошо модель обучилась, кроме как "на
   глаз" через `infer.py`.
